Features

Everything you need to monitor exceptions and uptime — without SaaS billing or vendor lock-in.

Exception ingestion
POST /api/log accepts the full client exception payload — HTTP context, user, stack — persisted as raw_exception with mapped columns and processed on the queue.
Issue codes
Auto-assigned codes like #BUG42 or #SHOP7 from group prefixes, with outages always mapped to #OUT. Paste a code anywhere to jump straight to it.
Fast triage
Open / Read / Fixed / Done in one click with an optional note, then move on to the next exception automatically. J K step through the list you came from.
Readable context
Stack traces with application frames highlighted and vendor frames collapsed, request method, URL, payload, client and affected user — plus how many times the same error was seen.
Navigation
⌘K palette to jump to any project, page or issue code, per-project tabs, a sidebar with live project health and cross-project search.
Uptime monitoring
Per-project pings every minute, ProjectOfflineException on failure, auto-recovery to DONE, email alerts for outage and restore, 30-day and 3-hour charts.
Workflow
Projects, groups, users, 2FA, API tokens, bulk actions, a “latest per error” view and optional read-only public shares at /e/{hash}.
Digests & pruning
Scheduled exception digests every minute; exceptions pruned after 24 months; uptime history kept for 30 days.
Admin REST API
Sanctum-protected CRUD for projects, groups, and exceptions. OpenAPI UI at /api/docs.
Privacy toggles
Hide HTTP headers or session data in the panel, exports and public pages via config/boogle.php / .env.
Client package
andreapollastri/boogle-client wires Laravel 9–13 apps to your Boogle instance in a few lines.

Install

PHP 8.3+, Composer, and Node. Any SQL database Laravel supports.

git clone https://github.com/andreapollastri/boogle.git
cd boogle
composer run setup

The setup script installs Composer deps, creates .env, generates the app key, migrates, installs npm packages, and builds assets.

Manual install

composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --force
npm install --ignore-scripts
npm run build

Run the tests

composer test

The suite runs on an in-memory SQLite database: ingestion, access control, triage, filters, search and uptime checks.

Quick start

From zero to a running panel in three steps.

01

Install & run

Clone the repo, run composer run setup, then start the stack with composer run dev.

02

Sign in

Default seeder admin: admin@users.test / password. Change the password right away from Profile.

03

Create a project

Add a project, open Installation for key + token, then wire a client app (next section).

Local stack

composer run dev

Starts the web server, queue listener, log tail, and Vite. For scheduler locally, also run php artisan schedule:work.

Demo data

Want to see a lived-in instance before wiring your apps? Seed the bundled demo.

php artisan migrate:fresh --seed --seeder=DemoSeeder

It creates six projects in three groups (with #SHOP, #OPS and #BUG prefixes), five users, about eighty exceptions in the boogle-client payload format with status history and notes, past and ongoing outages, and 30 days of per-minute uptime checks. Sign in as admin@users.test / password.

Heads-up: migrate:fresh wipes the database. Every project, person and domain in the demo is fictional (example.com), so don't leave the scheduler running against it — the uptime checks would flag every project as offline.

Client apps

Send exceptions from another Laravel application into this Boogle instance.

composer require andreapollastri/boogle-client
php artisan boogle:install

Set env vars from the project Installation page:

BOOGLE_KEY=<project_api_token>
BOOGLE_PROJECT_KEY=<project_key>
BOOGLE_SERVER=https://your-boogle-host.example/api/log

Laravel 11+

In bootstrap/app.php:

->withExceptions(function (Exceptions $exceptions) {
    Boogle::registerExceptionHandler($exceptions);
})

Laravel 9 / 10

In app/Exceptions/Handler.php register():

$this->reportable(function (Throwable $e) {
    Boogle::handle($e);
});
Laravel Where
11+ bootstrap/app.php → withExceptions
9 / 10 Handler::register() → reportable

Verify with:

php artisan boogle:test
Payload: the client posts key + token + full exception object. Boogle stores it in raw_exception and maps http / user for the panel.

Uptime

Each project can ping a URL and open an outage issue when it fails.

  • uptime_enabled — turn monitoring on or off
  • uptime_url — optional; falls back to the project url

On failure Boogle records a ProjectOfflineException and emails. When the service returns, the issue moves to DONE and a recovery mail is sent. The project chart shows the last 30 days.

php artisan projects:check-uptime

Admin API

Base path /api/admin. Auth: Bearer <sanctum-token> from an admin user.

  • Projects — list / create / show / update / delete
  • Groups — list / create / show / update / delete
  • Exceptions — global list, by project, show, update status
  • Ingestion — POST /api/log (project key + token, no admin bearer)

Interactive docs: /api/docs. Spec file: public/openapi.json (API v1.3.0).

Create tokens from the panel profile page.

Scheduler

One cron entry drives digests, uptime checks, pruning, and updates.

* * * * * cd /path-to-boogle && php artisan schedule:run >> /dev/null 2>&1
Command Schedule Purpose
exceptions:send-digests Every minute Email digests for open issues
projects:check-uptime Every minute Ping project URLs / outage issues
exceptions:prune-old Daily 04:00 Delete exceptions older than 24 months
app:update pending Every minute Start the update an administrator asked for (Updates)
app:update apply --auto Daily 04:00 Nightly update, while automatic updates are on (time: APP_UPDATE_TIME)

Updates

Boogle keeps itself on the newest build of its channel, with a database backup and rollback.

Administrators find Updates in the panel sidebar: the installed release, the newest build of the channel, Check now, Update to …, Force update, the channel and the nightly update.

  • Stable — the release tags (1.2.3; v1.2.3 and 1.2 work too) and nothing in between
  • Beta — the head of main, for a server you test on
  • Never backwards — a build is installed only when it contains the installed one. Back on stable after beta, Boogle keeps its main build until a release contains it
  • Force update — installs the newest build of the channel again, or one whose history differs; never an older one

Updates run every night at APP_UPDATE_TIME (04:00 by default) while automatic updates are on; one asked for on the page starts within a minute. Both start from the scheduler, so the cron entry is required.

Each update backs up the database (SQLite, MySQL/MariaDB, PostgreSQL; the newest 5 are kept in storage/app/updates/backups), installs the build, runs composer install --no-dev, builds the assets only when the release does not carry public/build, migrates, rebuilds the caches, restarts the queue workers and checks that Boogle boots. If a step fails, the previous code and the database come back; the log is on the page and in storage/app/updates/update.log.

Installations

Installation How it is updated
Git checkout (git clone, as in Install) In place: maintenance mode, detached checkout of the new build, build, migrations. Tracked files changed by hand stop the update; Force update discards them.
Releases of a deploy: releases/, current, shared/ (Cipi, Deployer) The build goes into releases/<build> next to the running one, shares its .env and storage, is built and migrated, then current points at it; Cipi's workers restart. A later cipi deploy keeps working.

The scheduler's user runs the update: it needs git, composer (npm when assets are built) and the database client tools (mysqldump/mysql, pg_dump/psql) on its PATH, and write access to the application.

Command line

php artisan app:update status          # the last check and the last run (JSON)
php artisan app:update check           # what the channel would install
php artisan app:update apply [--force] # update now
php artisan app:update channel stable  # or beta
php artisan app:update auto off        # or on

Configuration

Variable Notes
APP_UPDATES On in production; false turns updates off
APP_UPDATE_REPOSITORY Where builds come from (default: this GitHub repository)
APP_UPDATE_CHANNEL stable or beta until an administrator picks one (default stable)
APP_UPDATE_AUTO Nightly update on or off until an administrator switches it (default true)
APP_UPDATE_TIME When the nightly update runs, app timezone (default 04:00)
APP_UPDATE_BACKUP Database backup before each update (default true)
APP_UPDATE_ASSETS Build the assets when a release does not carry them (default true)
APP_UPDATE_PHP / _COMPOSER / _NPM / _GIT Tool paths, when the scheduler's PATH does not have them
Coming from before 1.0.0? Those installations don't have the updater yet: update or deploy them by hand one last time (git pull plus the production steps, or cipi deploy). From then on Boogle updates itself.

Production

Deploy without surprises. Cache config, keep the queue and scheduler running.

php artisan migrate --force
php artisan config:cache
php artisan route:cache
php artisan view:cache
php artisan queue:work --sleep=3 --tries=3 --timeout=120
Variable Notes
APP_URL Public HTTPS URL of this Boogle instance
APP_ENV / APP_DEBUG production / false
MAIL_* Required for digests and uptime alerts
QUEUE_CONNECTION Use database, Redis, or similar — keep a worker online
BOOGLE_UI_SHOW_HTTP_HEADERS Optional panel privacy (default true)
BOOGLE_UI_SHOW_HTTP_SESSION Optional panel privacy (default true)
Queue: notifications and digests go through the queue. Use Supervisor or systemd so queue:work restarts automatically. See the GitHub README for sample unit files.

Later releases install themselves from the scheduler: see Updates for what the scheduler's user needs.
